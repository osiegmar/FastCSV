CSV files are most commonly read sequentially from start to end. In some situations, like in graphical user interfaces,
you might need to read specific rows directly without having to read the entire file. FastCSV supports indexed reading
of CSV files, which allows you to navigate back and forth in the file in a random-access manner.

As CSV files do not include an index, FastCSV creates an index while reading the file. This index is stored in memory
and allows you to access rows directly. The index can optionally be stored in a file to avoid creating it every time
you read the CSV file.

:::note
The indexing process runs in the background while reading the CSV file. It is non-blocking, allowing you to start
reading the file while the index is still being created.
A status monitor is available to track indexing progress, making it ideal for graphical user interfaces.
:::

:::note[Index memory]
No CSV data is kept in memory, but the index is. It holds one page entry – roughly 40 bytes of heap – per
`pageSize` records:

```
index heap ≈ 40 bytes × ceil(recordCount / pageSize)
```

The index thus scales with the **record count**, not with the file size: a file of many tiny records needs a far
larger index than an equally sized file of few large records. A smaller page size buys finer-grained random access
at the cost of heap. In the worst case – a file of 1-byte records – the index takes roughly 40% of the file size
at the default page size of 100, but roughly 40 times the file size at `pageSize(1)`. Size the page accordingly
when indexing files of unknown shape.
:::

:::caution[Character set support]
Unlike `CsvReader`, `IndexedCsvReader` supports only **UTF-8 and single-byte character sets** (such as ISO-8859-1
or US-ASCII). Anything else is rejected with an `IllegalArgumentException` – this also applies to a character set
detected via a BOM header.

The index is built on byte level while the pages themselves are decoded and parsed on character level. That only
holds together if every ASCII byte is exactly its own character, and multi-byte character sets break this in one
of two ways:

- UTF-16 and UTF-32 encode ASCII as multiple bytes, and variable-width character sets (Shift_JIS, Big5, GBK,
  GB18030, ISO-2022-\*, …) place ASCII byte values *inside* the encoding of other characters, where the indexer
  mistakes them for a field separator, quote or line ending.
- Others are ASCII-transparent when encoding, but consume a following byte when *decoding*. EUC-JP, for example,
  decodes any byte pair starting `0xA1`–`0xFE` as a single character, swallowing a line feed the indexer has
  already counted as a record boundary.

For those files, either transcode to UTF-8 or read them with `CsvReader`, which works on characters and supports
any character set.
:::

The main API classes and methods for indexed reading are:

```java
// Index the CSV file with up to 5 records per page
IndexedCsvReader<CsvRecord> csv = IndexedCsvReader.builder()
    .pageSize(5)
    .ofCsvRecord(file);

try (csv) {
    // Find the last page in the index
    int lastPage = csv.getIndex().pages().size() - 1;

    // Output the last page
    List<CsvRecord> lastPageRecords = csv.readPage(lastPage);
    lastPageRecords.forEach(System.out::println);
}
```
